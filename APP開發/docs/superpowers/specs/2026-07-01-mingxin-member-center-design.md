# 明心福旺閣 會員中心 — 設計文件

- **日期**：2026-07-01
- **狀態**：設計待 laione 最終過目
- **作者**：sun（與 laione 協作 brainstorming）

---

## 1. 目的與範圍

替明心福旺閣的香供養會員做一個 **LINE 內建網頁（LIFF）會員中心**，讓會員用 LINE 登入後：

1. **客製自己的疏文**（疏文庫：可沿用舊疏文、可開新的，三種寫法）
2. **看歷屆已供養的內容與疏文**（疏文正本 + 疏文回覆）
3. **看活動後回傳的照片**

### 非目標（Non-Goals）

- **不含金流**：報名下單與付款維持走現有 `me1314888.com`，本系統不處理。
- 不做原生 App（不上架 App Store / Google Play）。
- 疏文庫**不強制綁死某筆訂單**——是會員的個人疏文庫，提交後進後台，laione 準備該場活動時取用。

---

## 2. 使用者與角色

| 角色 | 是誰 | 在系統裡做什麼 |
|------|------|--------------|
| **會員（供養人）** | 出錢下單、用 LINE 登入的人 | 綁定舊紀錄、寫疏文、看歷屆、看照片 |
| **受供人（疏文主體）** | 疏文個資對象，代供時是第三人 | 不登入；其個資存為會員名下的「個資記錄」 |
| **管理者（laione）** | 明心福旺閣營運者 | 審核綁定、看/取用會員提交的疏文、管理照片、跑匯入 |

### 代供（關鍵領域概念）

一筆供養有**兩個人**：**供養人**（下單者、綁定鑰匙）與**受供人**（疏文個資對象）。這解釋現有資料的怪象——`廖美垣(劉恩榜代供)`、每個活動夾都出現的「明心福旺閣」都是代供。

- 綁定與紀錄歸屬以**供養人**為鑰匙，不是疏文上的名字。
- 一個供養人名下可有多筆受供人不同的疏文。
- 接既有代供倫理硬規：疏文對象為「代供他人（非直系）」時，祈願內容限制為「結緣供養」，不能替求具體事項。

## 3. 架構

| 層 | 技術 | 職責 |
|----|------|------|
| 會員前端 | React + LINE LIFF SDK | 會員在 LINE 內開啟使用 |
| 管理後台 | 同一 React app 的 `/admin` 路由（laione 專用登入） | 審綁定、看疏文提交、管照片 |
| 後端 + 資料庫 | Supabase（Postgres + Auth + Storage） | 資料、圖檔儲存、身分驗證、權限 |
| 匯入工具 | 本機 Python 腳本 | 一次性 + 可重跑，把 GDrive/Dropbox 舊資料灌進 Supabase |

**為什麼 Supabase**：一套涵蓋資料庫、圖檔儲存（照片直接放 Storage）、以及以 Row Level Security（RLS）強制「會員只能讀自己名下資料」的權限控制。免費額度對現有量級（每場數十人、每年數十場）足夠。

**LINE 登入串接**：LIFF 取得 LINE user ID → 對應 Supabase `members` 表。RLS 以 LINE user ID 為主鍵鎖定資料可見範圍。

## 4. 資料模型（核心表）

### members（會員 = 供養人）
- `id`、`line_user_id`（唯一）、`display_name`、`phone`、`binding_status`（unbound / phone_matched / claimed / admin_bound）、建立時間

### person_profiles（個資記錄，可重用）
> 會員名下的個資，本人一筆、每個代供對象各一筆。跟單篇疏文解耦——個資穩定、疏文每場變。
- `id`、`member_id`（屬哪個會員）、`relation_type`（本人 / 代供他人）、`name`、`masked_name`、`birth_info`（生辰）、`address`、備註

### activities（活動）
- `id`、`temple_name`（廟）、`deity`（神明）、`solar_date`、`lunar_date`、`cutoff_date`（結單日）。接現有「香供養活動快取」。

### offerings（供養紀錄，一筆 = 一會員 × 一場活動 × 一受供人）
- `id`、`member_id`（供養人，綁定鑰匙）、`activity_id`、`person_profile_id`（受供人）、`petition_file`（疏文正本）、`petition_reply_file`（疏文回覆）、`photos`（該筆對應照片）

### shu_drafts（會員在 App 客製的疏文）
- `id`、`member_id`、`person_profile_id`（疏文對象）、`writing_method`（自由疏寫 / 模板式 / AI 引導）、`source`（新開 / 沿用舊疏文，沿用時記來源 offering/draft id）、`content`、`status`（草稿 / 已提交）、時間

### binding_requests（自助認領待審）
- `id`、`member_id`、會員填的比對資訊、`status`（待審 / 通過 / 退回）、laione 審核備註

## 5. 功能設計

### 5.1 綁定舊紀錄（三層，laione 指定 1+2+3）

1. **手機號自動配**：匯入時把供養人手機號一併建入。會員登入後驗手機號 → 自動認領名下所有 offerings。
2. **會員自助認領**：手機配不到時，會員填姓名/供養資訊申請 → 進 `binding_requests` → laione 後台審「確認是本人」。
3. **後台手動綁定**：laione 可直接把某 LINE 會員對到指定 offerings，為最終權限與修正手段。

### 5.2 我的歷屆供養

列出該會員名下所有 offerings（依活動日期排序），點開看：疏文正本、疏文回覆。以供養人為單位彙整（含其代供的受供人）。

### 5.3 活動回傳照片

每場活動一個相簿，可看大圖、下載。照片存 Supabase Storage，RLS 鎖定僅供養人本人可見自己名下照片。

### 5.4 客製疏文（疏文庫）

**開始時先問：用之前的內容，還是新內容？**

```
開始寫疏文
   │
   ├─ 用之前的內容 ──→ 調出該會員過往疏文，選一篇 → 套用沿用（可微調）
   │
   └─ 新的內容 ──────→ 先選疏文對象（本人 / 某個代供對象）
                          │  可調出該對象之前填的個資記錄，無需重填個資
                          │  （查無記錄才新填，並存成 person_profile 供日後重用）
                          ↓
                     選三種寫法之一：
                       1) 自由疏寫    — 會員自己寫，系統只存
                       2) 模板式      — 套用預設疏文內容，會員填空/挑選
                       3) AI 引導     — 系統一步步問，引導產出，再潤成疏文語感
```

- 疏文對象為「代供他人（非直系）」時，祈願內容自動限制為「結緣供養」（接代供倫理硬規）。
- 疏文模板/語感來源：既有疏文 docx 與 `shuwen-convert` skill 的轉換邏輯。
- 完成後可存草稿或提交；提交的疏文進 laione 後台，準備該場活動時取用。

## 6. 匯入工具（Python，本機）

掃 `香供養/{活動}/` 的 docx/pdf/xlsm 名冊 + Dropbox `香供養/活動資料/{活動}/` 照片，靠**檔名的姓名 + 名冊手機號**歸戶，建立/更新 activities、members、person_profiles、offerings、照片上傳 Storage。

- **可重跑**：跑一次匯入歷史，之後每場新活動再跑一次補資料（以活動+姓名去重）。
- 姓名隱碼（許O絜 vs 許婼絜）與代供標註（`廖美垣(劉恩榜代供)`）需在匯入時解析：括號內為供養人、括號前為受供人。

---

## 7. 隱私與權限

- 所有會員資料表以 RLS 綁 `line_user_id`，會員僅能讀自己名下資料。
- 受供人個資屬第三人：僅其**供養人本人**可見。
- 管理後台走獨立管理者身分，不套會員 RLS。

---

## 8. 分階段交付

| 階段 | 內容 | 價值 |
|------|------|------|
| **Phase 1（MVP）** | LINE 登入 + 手機綁定 + 我的歷屆疏文/回覆 + 活動照片 | 會員最想要的「看得到自己的東西」先上 |
| **Phase 2** | 客製疏文完整流程（沿用/新開 × 三寫法 + 個資記錄重用 + 代供限制） | 主動互動功能 |
| **Phase 3** | 自助認領審核後台 + laione 管理介面完善 + 匯入工具強化 | 營運可持續 |

---

## 9. 開放問題 / 風險

- **手機號資料齊全度**：Phase 1 手機自動綁定成敗取決於舊名冊手機號覆蓋率。匯入時需先盤點覆蓋率；不足處以自助認領（Phase 3）補。
- **姓名歸戶準確度**：隱碼、同名、代供括號格式若不一致，匯入需人工校對關卡。
- **LIFF 部署**：需在 LINE Developers 建 LIFF app 與 channel，並取得憑證（laione 端操作）。
- **疏文 AI 引導潤稿**：語感需過明心既有寫作紅線，Phase 2 再定細節。
